# Storage and artifact policy

Plamen's Git repository is the portable source of truth. An installed Plamen
tree, an audit workspace, or a developer's runtime directory is never a second
source tree. A new machine must be reproducible from a clean clone plus the
documented installer; it must not depend on copying a working machine's
generated directories.

This policy applies to development, releases, test runs, audits, and transfers
between operating systems.

## What belongs in Git

Commit artifacts that are required to understand, build, test, install, or
continue developing Plamen:

- source code, methodology, prompts, agent definitions, and platform adapters;
- package manifests, deterministic lock files, installer source, and launcher
  templates;
- architecture decisions, development goals, continuation instructions, and
  curated research written for this project;
- schemas, small deterministic conformance vectors, and minimal test fixtures;
- reproducibility manifests for external benchmarks, including an upstream
  repository URL, immutable revision, expected layout, and checksum where
  applicable; and
- sanitized validation summaries that contain no audit material, credentials,
  private filesystem paths, or machine identity.

Generated projections must be regenerated by the installer. Do not commit an
installed copy merely because it contains files that originated in Git.

## What stays local

The following are local or externally retained artifacts and must not be added
to the source branch:

- managed Python, Node, MCP, browser, compiler, or analyzer runtimes;
- virtual environments, package caches, dependency trees such as
  `node_modules`, bytecode, build output, and tool indexes;
- installer transactions, rollback snapshots, release staging trees, and
  repeated working-tree backups;
- audit targets, cloned benchmark projects, audit scratchpads, reports,
  run-bundles, worker outputs, terminal logs, and intermediate findings;
- browser profiles, session state, authentication material, signing keys,
  access tokens, shell history, and user configuration;
- downloaded third-party corpora, PDFs, vulnerability databases, and vector or
  RAG databases unless their redistribution rights and necessity are both
  established; and
- pytest temporary directories, probes, diagnostic captures, ad-hoc diffs,
  editor state, and operating-system metadata.

Some local artifacts are disposable because they are reproducible. Others,
such as audit evidence or provenance records, may need private retention. Both
classes stay outside Git; retention need does not make an artifact source code.

## Repository-size rule

Prefer a small fixture that proves a contract over a captured runtime or whole
audit workspace. If a required test asset is too large for normal Git:

1. reduce it to the smallest deterministic reproducer;
2. if reduction is impossible, store it in an access-controlled artifact
   service or release attachment;
3. commit only a fetch/verification manifest with an immutable identifier and
   SHA-256 digest; and
4. make tests skip with a clear explanation when the optional asset is absent.

Git LFS is not the default answer to generated data. Use it only after an
explicit repository decision covering availability, retention, and licensing.

## Public artifact manifests

A public manifest describes how to reproduce a non-private dependency. It must
not disclose where a developer stored it. Use repository-relative destination
paths and immutable upstream identities; never record an absolute local path,
username, host name, audit target, or credential-bearing URL.

Example:

```json
{
  "schema": "plamen.external-artifact.v1",
  "artifact_id": "example-fixture",
  "source_revision": "<immutable-revision>",
  "sha256": "<64-lowercase-hex-characters>",
  "bytes": 0,
  "destination": "tests/external/example-fixture",
  "required": false
}
```

The digest authenticates bytes; it does not grant permission to redistribute
them. Licensing and access controls remain separate requirements.

## Runtime boundaries

The installer owns installed launchers, agent projections, skills, runtime
environments, and transaction state. Development happens in a normal Git
checkout. Changes discovered while observing an installed tree must be applied
to the source checkout, tested there, and reinstalled through the supported
path. Directly maintaining both trees creates unreviewable drift.

Audit outputs belong to the audit workspace or a private evidence archive.
Tests may use sanitized, minimal reproductions derived from an audit only after
removing project content, findings, identities, absolute paths, and secrets.

## Cleanup invariant

Storage cleanup is a separate operation from source consolidation. Never
delete, truncate, overwrite, or deduplicate the old machine's Plamen material
until all of the following are true:

- the intended branch is pushed and visible remotely;
- a fresh clone has been made on the destination machine;
- the clone resolves to the expected commit and passes integrity checks;
- installation from that clone succeeds without relying on copied runtimes;
- the required smoke and platform tests pass on the destination machine;
- every retained private archive has a verified checksum and can be opened on
  the destination; and
- the operator has explicitly accepted the retention and deletion inventory.

Until those checks pass, old files are recovery material, even when they look
duplicated or disposable.
